§1The concept

Anthropic runs the agent loop. We run the tools.

Anthropic's managed agents are agents whose orchestration — model decisions, context management, error recovery — happens on Anthropic's infrastructure. The tool calls those agents emit can run anywhere: by default in Anthropic's own sandboxes, or, with a self-hosted environment, inside infrastructure you control.

The connection between the two halves is a per-environment work queue. When a session starts, Anthropic enqueues a work item. Your worker claims it, runs the agent's tool calls, posts results back. Anthropic keeps driving the agent loop and sends the next tool call. The worker is a half-mediator: it lives between Anthropic and the world the agent acts on.

Self-hosting is the right shape when the agent operates on data that can't leave your network boundary, calls internal services that aren't publicly routable, or runs under your own audit and compliance controls. The trade-off is operational — you run the queue worker, manage credentials, and own the runtime.

This project is one self-hosted environment, implemented on Cloudflare Workers. It mirrors the upstream cloudflare/claude-managed-agents layout where the scopes overlap, with intentionally narrower scope — one sandbox type, one example agent, no dashboard.

§2What we built

A worker, a credential model, an egress layer, an agent.

Four things, mostly orthogonal, sitting in one tree.

A Cloudflare Worker that implements Anthropic's self-hosted sandbox protocol. It receives session-status webhooks, verifies their signatures, polls the work queue, acknowledges and heartbeats claimed work items, and posts a stop when done. The protocol layer (URLs, HTTP methods, query parameters, body shapes) was inferred from public docs, then verified against the live beta API and pinned in tests.

An egress layer that intercepts every outbound fetch from tool handlers. It looks up policies in KV, resolves ${ref:NAME} placeholders against a secrets KV namespace, and injects the configured header before the request leaves. Agent code references credentials by name only — it never sees secret values. Fails closed when a referenced secret is missing.

A tool registry that defines the {name, schema, handler} triple. Handlers run in the parent worker context, not inside the isolate, so KV bindings and the egress fetch stay on the trusted side. Two generic example tools (echo, http_get) plus three GitHub tools (pr_diff, pr_files, pr_post_review) that exist for the first deployed agent.

An agent definition for PR review on the dotclaude repo. The agent's system prompt, model, and tool allowlist live in agents/pr-review/. A GitHub Action triggers it on pull-request events. GitHub specificity lives in the agent and the workflow, not in the runtime.

Plus the supporting bits: a per-agent email handler that catches inbound mail and writes it to KV; an interactive bootstrap script for first-time setup; a small ops.ts CLI for platform operations that need the org API key; a smoke test that signs a payload and posts it to wrangler dev; protocol regression tests; the cross-walk to upstream.

§3Architecture

One worker, two HTTP entry points, four roles.

The worker exports fetch for webhooks and email for inbound mail. Webhooks trigger the work-claim loop. Email lands in KV under agent:<id>:last. The work-claim loop hands each session to an isolate runner, whose tool calls dispatch back through the parent worker so KV, secrets, and the egress fetch stay on the trusted side.

end-to-end flow

The dotted box on the right shows the KV namespaces the worker reaches into: SECRETS holds raw credential values keyed by reference name; EGRESS_POLICIES holds the rules that match a host and inject a header; AGENT_INBOX holds the last email delivered to each agent. None of these are surfaced into the isolate — handlers in the parent worker context read them.

The two accent paths show the trust boundary: webhook arrival into fetch(), and outbound through the egress layer. Everything in between runs without the agent ever holding a credential value.

§4Two trust zones

The org key never crosses into the worker.

The hardest part to get right is the credential model. Anthropic exposes two distinct kinds of API key, and conflating them is the most expensive mistake available — putting an organization-scoped key on the worker host gives every agent tool call the ability to read it, which is exactly what the egress layer exists to police.

KeyScopeLives inUsed by
ANTHROPIC_API_KEY
org-wide		 Whole organization. Creates environments, agents, sessions, reads stats. ~/.env, read at script invocation only Developer-side scripts: scripts/ops.ts, register.sh, GH Actions. Never the worker.
ANTHROPIC_ENVIRONMENT_KEY
env-scoped		 One environment. Authorizes /work/* endpoints only. .dev.vars (dev) / wrangler secret (prod) The worker
ANTHROPIC_WEBHOOK_SIGNING_KEY
subscription-scoped		 One webhook subscription. Verifies inbound HMAC. Same as env key The worker
ANTHROPIC_ENVIRONMENT_ID Identifier (not secret) Same as env key The worker

The split is enforced by tooling. scripts/ops.ts reads the org key from ~/.env at invocation time and never writes it anywhere. scripts/push-env-keys.sh reads env-scoped values with read -s and pipes them straight to wrangler secret put over stdin — no command line, no shell history, no transcript. The .gitignore's repo-wide *secret* pattern catches typo'd filenames as a final defense.

§5The protocol, decoded

What the docs implied vs. what the API actually does.

The public docs cover the SDK helpers thoroughly but leave the raw HTTP shape partly to inference. We learned the rest by probing the live API and reading the TypeScript SDK source. Every shape below was verified end-to-end during the L4 staging deploy.

Endpoints (all ?beta=true, all Bearer auth with env key)

GET /v1/environments/{id}/work/poll
long-poll claim; block_ms, reclaim_older_than_ms query params
POST /v1/environments/{id}/work/{work_id}/ack
transitions queued → starting; required before heartbeats land
POST /v1/environments/{id}/work/{work_id}/heartbeat
extends the lease; optional desired_ttl_seconds
POST /v1/environments/{id}/work/{work_id}/stop
releases; {"force": true} for immediate
GET /v1/environments/{id}/work/stats
queue depth, pending count, oldest_queued_at, workers_polling

Webhook envelope

{
  "type": "event",
  "id": "<webhook-event-id>",
  "created_at": "...",
  "data": {
    "type": "session.status_run_started" | "session.status_idled" | ...,
    "id": "<session_id>",
    "organization_id": "...",
    "workspace_id": "..."
  }
}

Things that bit us

  • poll is GET, not POST. POST to /work/poll is interpreted as /work/{work_id} with work_id="poll" and returns a confusing 400.
  • reclaim_older_than_ms defaults to 5000. A scaffold runner that returns before the first heartbeat fires reclaims the same items it just acked — the worker chases its own tail. The fix is a longer window (we use 5 min).
  • The session id is at data.id, not data.session_id. Easy to miss; sessions named themselves consistently elsewhere.
  • The webhook is a wake-up signal, not a session-targeted dispatch. The poll returns FIFO; the session you process may not be the one whose webhook just fired. The SDK behaves the same way.
  • The env key's scope error is misleading. The 403 with "OAuth token does not meet scope requirement" was triggered by sending POST to a GET endpoint, not by an actual scope problem.

All nine pieces are pinned in tests/anthropic-protocol.test.ts — a future change that drifts breaks the test, not production.

V1.1 landed: runtime/isolate/runner.ts now opens the session event stream (GET /v1/sessions/{id}/events/stream), dispatches each agent.custom_tool_use through the tool registry, posts a matching user.custom_tool_result back, and handles dedup, 60s tool timeout, 30s end-turn idle window, and termination events. Skipped (intentional V1.1 simplifications): stream reconnect with backoff, history reconcile via events.list, result-post retries. At pr-review scale these simplifications cost nothing.

Proven end-to-end in 2 seconds: Session sesn_014aW6yyPWs9hoPYsGxmj6Y3 went idle → running → idle, mediated by the deployed worker, on the live Anthropic API. The worker successfully polled, acked, ran the stub runner, stopped, and Anthropic confirmed via session.status_idled.

§8Commands

The ones you'll reach for.

cd managed-agents/cloudflare

# first-time
bun install
bun run bootstrap                  # interactive .dev.vars setup

# day-to-day
bun run dev                        # wrangler dev on :8787
bun run smoke                      # signed payload → local dev
bun run test                       # 51 vitest tests
bun run typecheck                  # tsc --noEmit strict

# platform ops (reads ANTHROPIC_API_KEY from ~/.env)
bun run ops env list
bun run ops env create [name]
bun run ops env show <id>
bun run ops agent register [--dir agents/pr-review]
bun run ops session create --agent <id> --env-id <id> [--metadata @file.json]
bun run ops work stats --env-id <id>

# deploy (with the local CF config that holds account + KV ids)
bunx wrangler deploy --config wrangler.local.jsonc
bunx wrangler tail   --config wrangler.local.jsonc

# silent secret push to wrangler (values stay in your terminal)
bun run push-keys
