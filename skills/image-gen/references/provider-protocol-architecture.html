Image-gen architecture note

Provider scripts as small adapters, tested by a shared protocol.

This refactor keeps each image provider script understandable on its own, while making the comparison tools confident that every script behaves the same at the boundary.

Now Protocol Interface Tests Copy-Pastable Files Principles Evolution
Current decision

Keep provider-specific code in provider-specific files. Share only boring mechanics in scripts/common.py. Let tests define the interface that comparison tools depend on.

What changed

The refactor is architectural, but deliberately small.

We are not building a provider framework. We are tightening the seam between provider scripts and the rest of the skill. The scripts remain executable UV files that can be run directly. The comparison runner, review gallery, regeneration flow, and future prompt comparer can treat them as adapters with a stable command-line contract.

Provider scripts

generate_openai.py, generate_gemini.py, generate_imagen.py, and generate_fal.py stay provider-specific. API differences remain visible where they belong.

Common helper

scripts/common.py carries stable local mechanics: env loading, output paths, MIME handling, dimensions, and history logging. It is the only local helper import.

Protocol checker

The test suite now checks that provider scripts expose the same adapter surface before anyone discovers the mismatch during a comparison run.

Human docs

The README and maintenance workflow now name the adapter contract, so the design intent is not trapped in the test file.

Boundary

The protocol is the public interface for generation.

Every provider can have different API details, but each script must look the same from the outside. That is what lets comparison workflows call all enabled scripts without knowing about provider internals.

Executable
Each provider is a directly executable UV script with a shebang and PEP 723 metadata. uv run --script stays a fallback, not the main path.
Shared flags
The common surface is --prompt, --output, --output-dir, --model, and --check. Provider-specific options can still exist when they are real capabilities.
Predictable output
On success, the final stdout line is the resolved image path. That simple rule makes scripts easy for agents, shells, and higher-level tools to compose.
Local history
Successful generations record provenance unless history is explicitly disabled. The data is local and gitignored, but stable enough to analyze later.
No hidden framework
The checker allows only common.py as a local import today. That keeps the dependency graph flat and makes future copy-paste work feasible.
Interface tests

The protocol checker is an interface test, not just a lint rule.

Most tests verify implementation behavior. This pattern verifies the contract that other tools depend on. The comparison workflow should fail fast if a provider script drops a required flag, stops logging history, or stops printing the resolved output path.

Copyability

The long-term ideal is a provider file you can copy by itself.

We are not there yet because provider scripts still import scripts/common.py. That is acceptable for the current skill: it removes real duplication while keeping the shared surface small. But the architecture should continue moving toward files that can travel alone when needed.

future provider file checklist

#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.11"
# dependencies = [...]
# ///

must support:
  --prompt
  --output
  --output-dir
  --model
  --check

must do:
  create parent directories
  save the image with the correct extension
  record generation history, unless disabled
  print the resolved output path as the final success line
  avoid local imports, or include the shared helper code inline

The protocol checker gives us a migration path. Today it allows exactly one helper import. Tomorrow it can run in a stricter mode that proves a provider script is fully standalone.

Principles

The architecture should stay boring at the boundary and honest inside the files.

Small over clever

Use a small script per provider. Do not hide API differences behind an abstraction that makes debugging harder.

Protocol over inheritance

Define the interface with executable behavior and tests. A provider script conforms by doing the right things, not by subclassing a framework.

Copyable when possible

Prefer file-local clarity, direct execution, explicit dependencies, and stable flags. Shared code has to earn its place.

Free checks first

Most verification should run without credentials, network calls, or provider spend. Paid generation is an explicit later step.

Data accumulates locally

Prompts, outputs, rankings, winners, comments, and regeneration events should build a private training and evaluation trail.

Human review stays visual

The comparison UI should keep attention on images first. Details and mechanics should be available without dominating the task.

Evolution path

Where this can go next.

Phase 1 / now

Adapter protocol

Lock the current provider script interface with static and dry-run checks. Keep common.py as the only shared helper. Document the contract where humans and agents will find it.

Phase 2 / near

Contract outputs

Add an optional machine-readable self-description, such as --protocol or a dry-run JSON mode, so runners can discover capabilities without scraping help text.

Phase 3 / later

Standalone mode

Introduce a stricter checker mode that forbids local imports. Either inline the small shared runtime per provider file or generate standalone provider files from tested source.

Open question

Should copy-pastable provider files be handwritten, or generated from a canonical source plus a tiny embedded helper block?

Open question

Should the protocol checker remain static, or should every provider expose a cheap --protocol command that returns JSON?
