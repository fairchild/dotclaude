01 Why this exists

This printer has no LCD. The only local feedback is two indicator lights, and the only place a real error message appears is a web login (the Remote UI, or RUI) that most browsers on this network can't even reach reliably. Everything this skill does routes around that: it talks to the printer's own embedded IPP server, which answers structured questions — ink levels, error reasons, queued jobs — without authentication and without a browser.

The skill is disable-model-invocation: true, meaning it never triggers itself on keyword match. You reach it with /canon-printer, deliberately, the way you'd reach for a specific tool rather than have one appear because you said the word "printer."

The printer's IP, MAC, and subnet are network-identifying details for one specific home device, so they live in ~/.env — CANON_PRINTER_IP, CANON_PRINTER_MAC, CANON_PRINTER_SUBNET — not in this repo. Nothing sources ~/.env into agent shells, so the script extracts exactly those three lines from it at startup (no eval); the admin password in the same file is deliberately never read.

Those entries are an optimization, not a requirement. Malformed values are warned about and ignored; a stale or missing IP self-heals — the script pings the configured address before any network command, and on no answer re-finds the printer over Bonjour (it advertises ty=Canon iX6800 series and answers mDNS even while asleep), proceeding against the mDNS hostname. The first DHCP lease move after this was built got caught exactly this way. A missing subnet derives from the default-route interface. The only hard failure is a printer that's powered off and absent from mDNS.

Runtime state the printer can't hold for itself — what paper is physically loaded, ink-level history — lives outside the repo at ~/.local/state/canon-printer/.

02 Three layers, three vocabularies

A stuck print touches three separate systems, and each one only knows part of the story. Reading the wrong one wastes time — this is the map that keeps them straight.

macOS CUPSlocal spooler

What lp, lpstat, and System Settings' printer pane see. It can silently disable a queue (Unable to add document to print job) and then just sit on submitted jobs forever — this has happened twice this session, and it's invisible from the printer's own side entirely. Check it with lpstat -p -l; revive it with cupsenable.

Printer IPPport 631

The printer's own embedded print server. This is the primary source of truth for this skill — status and jobs query it directly, no login required. It reports printer-state, ink marker-levels, and printer-state-reasons — but that last one is nearly always the generic other-error. It does not carry numbered Support Codes.

RUIport 80, login

The web admin. Slower, needs the admin password, and blocked outright for Chrome/Firefox on this Mac by a Little Snitch rule (Safari is unaffected — see Errors we've seen). Its one advantage: it's the only place a numbered Support Code (5100, 2100, ...) actually appears. When IPP's other-error isn't enough to diagnose something, this is the fallback, read by a human — this skill does not and will not log in on its own.

04 Printing & queues

Two local CUPS queues exist on this Mac, and print exists specifically to hide the difference:

sizeQueueWhy
letter (default)Canon_iX6800_seriesAuto-generated AirPrint queue. Fine for standard sizes.
13x19 / superb / a3+Canon_iX6800_series_13x19Canon's real driver, added by hand. The AirPrint queue never advertises Super B and can't negotiate a hand-typed 13×19 custom size with this printer's firmware — that combination stops the job with Support Code 2100 even when the dimensions are correct.
13x19-borderless / letter-borderless / …Canon_iX6800_series_13x19The native PPD's .FullBleed presets — edge-to-edge posters and photos. Supported bases: 13x19, letter, a4, a3, tabloid, 4x6, 5x7.

The native driver was already sitting on this Mac (the Canon BJPrinter package), just unused by the default queue. Its PPD defines a proper 329x483mm / A3+ 13"x19" 33x48cm preset — that's the one this printer's firmware actually accepts.

Neither queue knows what paper is physically loaded. That used to be the one thing print couldn't automate; now it's tracked. paper <size> records what's in the rear tray, and print refuses a job whose physical size disagrees with the record — the exact condition that halts the printer with Support Code 2100 — with a message naming the three ways out (swap and re-record, print at the loaded size, or force past a stale record). 13×19 stock still has to feed from the rear tray, not the front cassette. If a mismatched job does reach the printer, cancel-job clears it once the sizes agree; that's the printer's own size-safety check doing its job.

print also self-heals the other silent failure on this list: CUPS has paused a local queue mid-session with no visible cause and sat on submitted jobs forever, invisible from the printer's side. Every print (and the bare full check) now runs lpstat -p and cupsenables a disabled queue before submitting.

Documents, posters, and paper as an output channel

print-doc is the render path: Claude writes styled HTML with an @page CSS rule sized to the target paper, headless Chrome converts it to PDF deterministically, and the result goes through the same guarded print. Markdown is rejected on purpose — render it properly first. This one verb is what turns the printer into an output channel for agents: a morning agenda (calendar + weather + backlog) printed on a schedule, generated art at 13x19-borderless, N-up photo sheets with cut marks, recipes, packing lists, mazes for kids.

The other half of unattended printing is Auto Power On — a one-time human setting (RUI or the Canon IJ Printer Utility) that wakes the printer when a job arrives. Without it, Auto Power Off means every agent print while the printer sleeps needs a human at the button first.

If this skill ever runs on a different Mac, Canon_iX6800_series_13x19 needs recreating there — the full lpadmin command is in SKILL.md.

05 Errors we've seen

informational operator-fixable hardware fault

Ink exhaustedother-error

One marker-levels entry at or near 0 in status. Match the position against marker-names to name the cartridge (Magenta, Black(BK), Yellow, Black(PGBK), Cyan). printer-state goes to stopped; spool-area-full-report often rides along as a side effect of jobs backing up, not a separate cause.

Stuck job, ink is fineother-error

Check jobs: a job sitting at processing-stopped / job-stopped with 0 sheets completed is almost always a media mismatch — the size or media type it requested doesn't match what's loaded. See Printing & queues. cancel-job, fix the mismatch, resend.

Carriage obstructionSupport Code 5100

Symptom: a loud/grinding noise mid-print, then a halt, then the Power and Alarm lamps blink alternately — not a counted number of flashes, just back-and-forth, pause, repeat. IPP only ever shows generic other-error for this; the numbered code is RUI-only. Cause, almost always: something physically blocking the print head carriage — jammed paper, or leftover protective tape/cap from a cartridge swap (a strong suspect right after replacing ink, since that's exactly when loose tape ends up in the carriage's path). Fix: power off, open the cover, clear the obstruction without touching other internals, power back on. If it recurs on a clean path, it's a genuine hardware fault (bent rail, failed motor, damaged encoder strip) — service territory, not something further commands can reach.

Paper size mismatchSupport Code 2100

"The paper size in the print settings and the size of the loaded paper do not match" — exactly what it says. The fix is matching the two, not a network or driver problem by itself (though see Printing & queues for the specific case where the AirPrint queue can't reach a working combination at all).

Unreachable — every port filtered, ARP still cached

Printer's asleep or fully powered off (Auto Power Off, especially right after an ink-out halt), not a network fault. Check the panel or press a button to wake it, then retry. The standing fix is enabling Auto Power On (see Printing & queues) so an arriving job wakes it instead of a human.

Reachable in Safari, ERR_ADDRESS_UNREACHABLE in Chrome/Firefox

Little Snitch filtering those two processes specifically, confirmed by Socket closed during DPI without data lines naming the browser and the printer's IP in /usr/bin/log show --last 20m --predicate 'process CONTAINS "littlesnitch"' --style compact. Fix in Little Snitch's rules, not here.

Gotcha: call /usr/bin/log by full path. Bare log is a zsh builtin (a math function) that shadows the real command and fails with a confusing too many arguments error instead of running.

/rui/index.html redirects to /errindex.html

Not a device error page — just the login-required screen. Unauthenticated access to the RUI 401s and its JS renders ERR_INVALID_PWD. Use status over IPP for real state instead of reading this page as diagnostic.

Port 443 always filtered

Expected — this printer doesn't serve HTTPS at all. Firefox's HTTPS-only mode will retry 443 and fail before falling back to the plain HTTP on port 80 that actually works.

06 Reading a nozzle check

Run after clearing any physical fault, to confirm the print head itself came through undamaged. Two columns of short bars, one per ink pass:

PGBK
C
M
Y
BK

Solid, continuous, unbroken end-to-end — healthy, no cleaning needed. A faded or missing segment partway down a bar — that channel is clogged; run Cleaning (then Deep Cleaning if that doesn't clear it) before assuming a fault caused lasting damage. A carriage obstruction (5100) stops head movement, not ink flow — a clean nozzle check right after clearing one is the expected, good outcome, which is exactly what happened the one time we've hit this.

You don't have to interpret the sheet yourself: photograph it and hand Claude the image. It reads the bars against these criteria and names the specific channel and the recommended step. The same move — print, photograph, compare — works as a general verification loop for color-critical output.

07 Boundaries

An admin password for the RUI may exist at runtime as $CANON_PRINTER_ADMIN_PASSWORD (sourced from ~/.env, on this machine). This skill does not read or use it. Logging into the RUI — by browser form-fill or by a scripted request — stays out of scope regardless of how the credential is made available. Every command here works fully unauthenticated over IPP; anything that genuinely needs the RUI (like triggering a Nozzle Check from the web UI, rather than the physical panel) requires logging in yourself, in your own browser session.
